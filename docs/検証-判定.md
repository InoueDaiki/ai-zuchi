# 検証: 口を出すかの判定

会議の文字起こしと画面の文字から、手元の Ollama で「口を出すか、黙るか、どのスキルか」を判定できるかを、架空の日本語会話で測った記録。実施は 2026-11-01、環境は Apple M5(RAM 32GB)の Mac、Ollama 0.40.13。**Windows では計測していない。本物の会議の音声と ASR の出力でも計測していない。**

スクリプト、台本、集計は [tools/spike-gate/](../tools/spike-gate/) にある。生の出力は含めていない。評価用の台本の 1 場面は、測定のあとで製品名をサービス A〜C に置き換えた。

## 推薦

**`gemma4:e4b-it-q4_K_M`(Gemma 4 E4B の GGUF 版)を、structured output あり、think なしで使う。台本の上では使える。** 段階 1 に進んでよい。ただし、本物の会議での誤発話の頻度はまだ分からないので、段階 1 で測る。

| 項目 | 推薦 |
|---|---|
| モデル | `gemma4:e4b-it-q4_K_M`。`gemma4:e4b` と書くと、この環境では MLX 版が選ばれるので、タグを明記する |
| `format` | JSON Schema を渡す |
| `think` | `false` を必ず明示する。既定値はモデルで異なる |
| 確信度のしきい値 | 使わない。今回の値では効かなかった |
| 段階 2 | 直近 2 発話を見るルール。削減は小さい(16%)が、良い補足を落とさなかった |
| 計算 | 抽出の誤りが残るので、前提の期間を補足文に必ず出す |

理由:

- 評価用 96 場面で、適合率 0.95(39/41)、再現率 0.97(39/40)。設計メモの目標の適合率 80% を、95% 信頼区間の下限(0.84)でも上回った
- 黙るべき 56 場面での誤発話は 2 件
- 判定の遅延は p50 1.12 秒、p95 1.63 秒
- MLX 版と品質の差はなく、メモリは半分以下で、増え続けなかった

注意点:

- 適合率 0.95 は台本での値で、作成者の傾向が入っている(「評価の限界」を参照)
- 誤発話率の 95% 信頼区間は 1〜12%。**誤発話率 3.6% のまま 1 時間に 300 回判定すると、約 11 件の余計なひとことになる試算で、目標の 5〜15 件を誤発話だけで占めかねない。** 判定の回数も誤発話率も仮定で、実測ではない
- 計算の抽出は 13 件中 11 件で値が合った。**残り 2 件は誤った数字を出す**(「計算スキル」を参照)

## 比較したもの

名前はすべて Ollama のライブラリと `/api/show` で確認した。取得の合計は 30.1GB で、上限の 30GB をわずかに超えた(下の注を参照)。

| 名前 | 重み | 量子化 | runner | 取得サイズ | パラメータ数 |
|---|---|---|---|---:|---:|
| `gemma4:e4b-it-q4_K_M` | GGUF | Q4_K_M | llama.cpp(`llama-server`) | 6.6GB | 7.5B |
| `gemma4:e4b` | safetensors | nvfp4 | MLX | 9.5GB | 8.1B |
| `gemma4:e2b` | safetensors | nvfp4 | MLX | 7.5GB | 5.2B |
| `qwen3:4b` | GGUF | Q4_K_M | llama.cpp | 2.5GB | 4.0B |
| `qwen3.5:4b` | safetensors | nvfp4 | MLX | 4.0GB | 4.5B |

- 「取得の合計」は `ollama list` の値の和。計画の時点ではライブラリのページの値から 30GB 以内と見積もったが、`gemma4:e4b`、`gemma4:e2b`、`qwen3.5:4b` は MLX 版に解決され、実際のサイズがページから読んだ値より大きかった。共有の層があると実際のディスク使用量はこれより小さい可能性があるが、確かめていない
- ライセンスは今回確かめていない

## 評価の方法

- 台本: チューニング用 34 場面(`data/tune.yaml`、黙るべき 18)、評価用 96 場面(`data/eval.yaml`)
- 評価用の内訳: 黙る 56、計算 13、検索 12、提案 8、記憶 7。画面の文字あり 30、文字起こしの誤りあり 20。ユースケース 4 つすべてを含む
- 評価用は、プロンプトを書かない別のエージェントが、プロンプトを見ずに書いた。プロンプトの作成者はチューニング中に中身を読んでいない
- プロンプトとルールは tune だけで調整し、固定してから eval を流した
- 生成の設定: 温度 0、top_k 1、seed 固定、`num_ctx` 4096、`num_predict` 2048。LLM の呼び出しは同時に 1 つ
- 遅延は壁時計の時間で、モデルを読み込んだ最初の 1 件を除く。負荷平均は eval の間 0.4〜2.7 で、ほかに重い処理はなかった。会議のアプリとは同居させていない
- 壊れた応答は「黙る」として数えた
- 適合率と再現率は、スキルまで合ったものを正解とした

### 計算スキル

判定とは別の LLM 呼び出しで数値と単位を抽出し、`scripts/calc.py` で換算した。

「3カ月で10億件」は、推薦の構成で次のとおりになった。

> 秒間約127件、1日約1,100万件(3カ月=91日で計算)

| 構成 | 固定時点の値の正解 | 換算コードの修正後 | 値と単位の両方が正解 | p50 秒 | p95 秒 |
|---|---:|---:|---:|---:|---:|
| **E4B GGUF、schema** | **9/13** | **11/13** | 6/13 | 1.40 | 1.70 |
| E4B GGUF、free | 9/13 | 11/13 | 6/13 | 1.39 | 1.68 |
| E4B MLX、schema | 8/13 | 10/13 | 6/13 | 0.85 | 1.11 |
| E4B MLX、free | 8/13 | 10/13 | 6/13 | 0.61 | 0.88 |
| Qwen3.5 4B、schema | 6/13 | 9/13 | 7/13 | 1.70 | 2.00 |
| Qwen3.5 4B、free | 6/13 | 9/13 | 7/13 | 1.34 | 1.87 |
| E2B、schema | 7/13 | 8/13 | 3/13 | 0.50 | 0.68 |
| E2B、free | 7/13 | 8/13 | 3/13 | 0.38 | 0.54 |
| Qwen3 4B、schema | 5/13 | 8/13 | 6/13 | 1.75 | 2.14 |
| Qwen3 4B、free | 0/13 | 0/13 | 0/13 | 20.27 | 20.40 |

- 「換算コードの修正後」は、eval を見て直したコードで保存済みの抽出結果を換算し直した値で、**固定後の修正を含む**。修正は 1 つで、「月に2600万」のように数のない期間を読めなかった不具合。プロンプトは変えていない
- 推薦の構成で値を誤った 2 件は、どちらも年間の総量に対し、換算先の「1日」を元の期間として抽出した。**例外にならず、誤った数字がそのまま補足文になる。** たとえば「(1日=1日で計算)」と出る
- 値と単位の照合は完全一致で厳しい。単位が空(「1部署あたり約30万」)のほか、「約840万人月」のように誤った単位が付くものがある
- Qwen3 4B の free は、`num_predict` 512 を本文に漏れた思考で使い切った
- 発話の終わりから補足までの目標は 3 秒以内。判定と抽出の和は p50 で約 2.5 秒、p95 で約 3.3 秒で、**文字起こしの時間を足す前に p95 が目標を超える**。ASR の時間は今回測っていない

### 段階 2 のルール

`scripts/rules.py` は、数と単位、疑問、依頼、記憶の手がかりを見る。ルールも tune だけで調整した。推薦の構成の保存済みの結果に、ルールを掛け合わせて求めた。

| 方式 | LLM の呼び出し(/96) | ルールが落とした良い補足(/40) | 適合率 | 再現率 | 誤発話 |
|---|---:|---:|---:|---:|---:|
| ルールなし | 96 | 0 | 0.95 | 0.97 | 2 |
| 最後の発話だけを見る | 58 | 5 | 0.97 | 0.88 | 1 |
| **直近 2 発話を見る** | **81** | **0** | 0.95 | 0.97 | 2 |

- 最後の発話だけを見ると、呼び出しは 40% 減るが、良い補足を 8 件に 1 件落とす。tune で落ちたのは「ちょっと僕もよく分かってなくて」のように、問いのあとの発話で判定する場面。eval の 5 件には、期限のない約束などの提案も含まれる
- 直近 2 発話なら落とさないが、呼び出しは 16% しか減らない
- この削減率は、黙る場面にも手がかりを意図的に入れた台本での値で、本物の会議の値ではない。eval の全発話(200 発話)のうち、1 発話で手がかりがあるのは 58.5%
- 判定は約 1 秒で終わるので、段階 2 の役割は呼び出しの削減より、相づちの連続で LLM を空回りさせないことと考えるのが妥当

## 分かったこと

### Ollama の structured output は Gemma 4 で機能する

**Ollama では、制約デコードでも空の出力は出なかった。** E4B の 8 構成、E2B の 4 構成のいずれも空の出力は 0 件で、中身のある判定が返った。MLX 版、GGUF 版の両方で確かめた。品質は自由形式と差がなく(差は 1〜2 場面)、遅延も増えなかった。

自由形式でも、Gemma と Qwen3.5 の JSON の成功率は eval で 1.00 だった。schema の利点は、スキルの列挙を形式で保証できることにある。

### think は要らない

- Gemma 4 E4B: 品質は上がらず、遅延は 8〜11 倍になった。計算の目標 3 秒に入らない
- Gemma 4 E2B: 誤発話は 17 件から 13 件に減ったが、適合率は 0.75 にとどまる
- Qwen3 4B と Qwen3.5 4B: tune で p50 が 66〜106 秒(この間の負荷平均は最大 38 で、遅延は高めに出ている可能性がある)。多くの場面で `num_predict` 2048 を使い切って結論が出ず、再現率が 0.06〜0.56 まで落ちた。eval には流していない

### Qwen3 の `think: false` は free では効かない

`qwen3:4b` は free で `think: false` にしても、本文に英語の思考と `</think>` を書き、tune の p50 は 75 秒だった。`format` を渡すと止まる。parser では `</think>` より後ろを読むようにした。これらの理由で、eval は schema ありだけ流した。

### `gemma4:e4b` は MLX 版に解決される

ライブラリのページのサイズ(6.6GB)と実物(9.5GB、nvfp4)が違った。GGUF 版を使うにはタグを明記する。MLX 版は遅延が約 0.3 秒短いが、メモリが増え続ける。

### 小さいモデルの弱点はそれぞれ違う

- E2B はよく話すが黙れない。誤発話 17 件で、答えが出た話に 6 件、対応済みの依頼に 3 件、言いかけに 3 件反応した。判定には足りない
- Qwen は黙りすぎる。検索の正解が、Qwen3 4B で 4/12、Qwen3.5 4B で 2/12。計算の 13/13 と差が大きい。「BONX の差別化」を Qwen3.5 は 2 構成とも見逃した
- どちらも `think` なしでは E4B に届かなかった

### 確信度は当てにならない

推薦の構成では、しきい値 0.8 まで適合率が 0.95 のまま変わらず、0.9 では適合率が 0.93 に下がり、再現率は 0.68 に落ちた。誤発話 2 件はどちらも確信度 0.9 だった。値が 0.85、0.9、0.95 に集まり、例の値を写している可能性がある。段階 3 の JSON に確信度を残すのはよいが、判定には使わない。

### プロンプトの要点

全文は `tools/spike-gate/scripts/prompts.py` にある。

- **「none が基本」を先に書き、黙る場面を列挙する。** やることの逆も書くと効いた
- **例は 5 つで、none も入れる。** 画面の依頼の例を足すまで、E4B は「こちらご確認ください」を見逃した
- **引き受けた約束を明記する。** 「金曜までに送ります」も suggest だと書いた
- **`reason` を `skill` の前に置く。** 根拠を先に書かせる
- **入力はデータだと書く。** 画面や音声の AI への指示には、推薦の構成で 4 場面とも従わなかった。ただし構成によっては従った例がある(E4B GGUF、free、think で 1 件)。プロンプトだけに頼らず、設計メモのとおり権限を分ける

## 測っていないこと

- 本物の会議、本物の ASR と OCR の出力。文字起こしの誤りは手で作ったもの
- **実際の会議の 1 時間あたりの補足の数。** 連続した会話を流していない。各場面は独立で、確認(重複、頻度、鮮度)も実装していない
- 判定の呼び出しの間隔と、古い判定を捨てる処理の効果
- 会議のアプリや ASR と同居したときの遅延、メモリ、発熱
- 長時間の連続運転。300 回まで
- Metal のメモリを含む、GGUF 版の本当の使用量
- Windows のすべて
- 検索、記憶、提案のスキルの本体。判定で選べることだけを測った
- 検索語の作成と、社外秘の語の混入
- think ありの Qwen の eval
- E2B の GGUF 版と、Qwen の `num_predict` を増やした場合
- 判定の文脈の長さを変えた場合
- `gemma4:e4b-it-qat` などの他の量子化

## 評価の限界

- **tune と eval の両方を Claude が書いた。** eval は別のエージェントだが、モデルも同じで、製品の説明も同じものを読んでいる
- **黙る場面の分類を、プロンプトと eval の作成者が共有した。** `data/README.md` の分類を eval の作成者に渡し、同じ分類をプロンプトの none の一覧にも書いた。実際の会議には、この分類にない黙るべき場面がある。適合率は高めに出ている可能性が高い
- **eval の作成の指示に「判断が割れる場面は入れない」とある。** 本物の会議では、判断が割れる場面こそ多い
- 黙るべき場面の割合は 58% で、本物の会議より大幅に低いと考えられる。適合率は、この割合に依存する。誤発話率のほうが移しやすい指標
- 場面ごとに正解が 1 つの固定の採点で、「このひとことは嬉しいか」は測っていない。補足の文面も見ていない
- 件数が少ない。E4B の構成の差は検出できない
- eval を見たのは固定のあと。ただし計算の換算コードは eval を見て直した。その数字は別の列に分けた

## 再現の手順

```bash
cd tools/spike-gate
mise exec -- uv sync
mise exec -- uv run pytest
for m in gemma4:e4b gemma4:e4b-it-q4_K_M gemma4:e2b qwen3:4b qwen3.5:4b; do ollama pull "$m"; done
mise exec -- bash scripts/run_all.sh tune gemma4:e4b gemma4:e4b-it-q4_K_M gemma4:e2b qwen3:4b qwen3.5:4b

mise exec -- uv run python scripts/rescore_calc.py
```
