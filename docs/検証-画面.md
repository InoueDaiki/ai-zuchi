# 検証: 画面

`crates/zuchi-screen` の設計判断、合成画像での測定、本人が実行する確認手順を残す。2026-11-01 時点。

## 結論

- macOS の Vision は、合成画像では日本語を十分に読めた。Retina 相当の画像で CER 1.16%、1 枚 0.6 秒前後
- 変化があるときだけ読むので、待機中の CPU は目標の範囲に収まる見込み。ただし実際の画面の取得を含まない値で、**実画面では未測定**
- 実画面の取得(ScreenCaptureKit)は、権限がない環境で作業したため動かしていない。本人の確認が必要
- Windows はコンパイルの確認までで、実機では動かしていない

## 設計の判断

| 判断 | 内容 | 理由 |
|---|---|---|
| macOS の呼び出し | Swift の補助プログラムを作らず、objc2 系のクレートで直接呼ぶ | 必要な API(`SCScreenshotManager`、`VNRecognizeTextRequest`)はすべて `objc2-screen-capture-kit` と `objc2-vision` にある。1 回撮るだけなので、Core Audio tap のような難しさがない。別の処理へ画像を渡さずに済み、`cargo build` だけで作れる。そのため `native/macos-screen/` は作っていない |
| 取得の単位 | 画面全体ではなく、最も手前の窓だけを 1 枚撮る | その窓だけが写るので、自分のオーバーレイや対象外の窓が画像に入らない。`ScreenText` のアプリ名と題名も正確になる。Windows.Graphics.Capture には特定の窓を除いて画面を撮る方法がなく、両 OS でそろえられる |
| 取得の方式 | 連続の取得ではなく、周期ごとの 1 枚の取得 | 1.5 秒に 1 回なら、ストリームを開き続ける必要がない |
| 対象外の判定 | アプリの識別子と、題名やアプリ名に含まれる語で判定する。手前の窓が対象外なら、その周期は何も撮らない | 銀行は Web で使うことが多いので、題名でも止める |
| 判断できない窓 | 題名やアプリが分からない窓は読まない | 迷ったら黙る。読めない窓が増えたら見直す |
| タブの切り替え | OCR の直前に窓の一覧を取り直し、窓か題名が変わっていたら読まない | 取得と OCR の間に銀行のタブへ替わった場合に備える |
| OCR の時機 | 変化のあと、次の周期でも同じ画面なら読む。変わり続けるなら 5 周期に 1 回読む | スクロールの途中を読まず、動画で読み続けないようにする |
| 差分 | 行を正規化して窓ごとに最大 2000 行を覚え、直前の画面の行とは近似でも比べる | OCR の揺れで同じ行を流し直さないようにする |

### 設計メモとの違いと、やっていないこと

- 設計メモの「変わった領域だけを OCR」ではなく、窓全体を読む。行の差分を安定させるためで、1 回の時間に問題がなければこのままにする
- 設計メモの「パスワード欄の周辺も読まない」は未実装。窓の単位で止めるだけで、普通のサイトのログイン画面は題名に対象外の語がなければ読む
- 題名は他人が決められるので、対象外の語を含まない銀行のページは防げない。URL は見ていない
- 手前の窓だけを読むので、背面や別のディスプレイの窓(本人が見ている会議の画面共有など)は読まない

## OCR の測定

### 条件

- 機材: Apple M5、macOS 26.6.2。Vision の `VNRecognizeTextRequest`、`ja-JP` と `en-US` を指定
- 画像: `bench/gen_screens.py` で作った架空の 9 画面(チャットの明暗、メール、表、Web 記事、コード、スライド、11 pt の小さな文字、淡い文字)。1440 x 900 の各画面を 3 種類で作った
  - `1x`: 等倍。外付けの通常のディスプレイを想定
  - `2x`: 2 倍。Retina を想定
  - `share`: 等倍を JPEG の品質 30 で圧縮。会議の画面共有を想定
- CER: 正解の各行と、OCR の結果の中で最も近い部分との編集距離を、文字数で割ったもの。空白と全角半角の違いは無視する。行の順番は評価しない
- 時間: 各画像 3 回の中央値

実際の画面とは、文字の描画(サブピクセルなど)が異なる。**この値は実画面の精度を保証しない。**

### 再現の手順

```bash
mise exec -- uv run crates/zuchi-screen/bench/gen_screens.py target/screen-bench
mise exec -- cargo run -p zuchi-screen --release --example ocr_bench -- target/screen-bench
```

### 種類ごとの結果

| 種類 | 読み方 | CER | 完全一致の行 | 時間の中央値 |
|---|---|---:|---:|---:|
| 1x | 標準(言語補正あり) | 1.12% | 94.5% | 609 ms |
| 1x | 言語補正なし | 1.39% | 91.5% | 285 ms |
| 2x | 標準(言語補正あり) | 1.16% | 96.3% | 620 ms |
| 2x | 言語補正なし | 1.12% | 95.1% | 292 ms |
| share | 標準(言語補正あり) | 3.53% | 83.5% | 568 ms |
| share | 言語補正なし | 4.43% | 78.0% | 277 ms |

- 標準の読み方を採用する。補正なしは約 2 倍速いが、圧縮された画面で弱くなる
- `VNRequestTextRecognitionLevelFast` は日本語に対応していなかった(`supportedRecognitionLanguages` に `ja-JP` がない)。起動時に `CaptureError::Unsupported` で分かる
- 時間は画像の大きさにほとんど左右されず、文字の量で決まる

## CPU の測定

`ocr_bench --simulate` で、取得の部分だけを偽物に替えて、変化の検知、OCR、差分を実際に 60 秒動かした。画像は 2880 x 1800、周期は 1.5 秒。起動の直後の 1 回の OCR を含む。

| 画面の変わり方 | OCR の回数 | CPU(1 コアを 100%) | 最大メモリ |
|---|---:|---:|---:|
| 変わらない | 1 | 2.6% | 303 MB |
| 12 秒ごとに変わる | 5 | 12.6% | 349 MB |
| 周期ごとに変わる | 8 | 19.2% | 339 MB |

- 実際の取得(ScreenCaptureKit)の負荷と、取得の待ち時間は含まない
- Vision が GPU や Neural Engine で使う分は、この CPU の値に含まれない可能性がある
- OCR の処理が初めて走るとメモリが約 300 MB 増える。常駐のメモリとしては軽くない
- 設計メモの目標「待機中の CPU は 1 コアの 10% 以内」は、変わらない画面では満たす。よく変わる画面では超えるので、実画面の測定のあと、周期を延ばすか、読む回数に上限を置くかを決める

## 本人が実行する確認手順(macOS)

権限の許可は本人にしかできない。`screen_check` は読んだ文字も画像も表示、保存せず、回数だけを出す。

1. ビルドする

   ```bash
   mise exec -- cargo build -p zuchi-screen --release --examples
   ```

2. 権限を確かめる

   ```bash
   ./target/release/examples/screen_check 30
   ```

   `権限エラー: 画面収録の権限がありません` と出て、終了コードが 2 なら権限がない。OS の確認は出ない。

3. 権限がなければ、OS の確認を出す

   ```bash
   ./target/release/examples/screen_check --request
   ```

   システム設定の「プライバシーとセキュリティ」→「画面とシステムオーディオの収録」で、実行したターミナルのアプリを許可し、そのアプリを再起動する。権限はターミナルのアプリ(製品版では ai-zuchi)に与えられる。

4. 手順 2 をもう一度実行し、30 秒の間に普通の窓を操作する。`取得` と `OCR` の回数が増え、`失敗 0 回` なら動いている
5. 1Password や、題名に「銀行」を含むページを手前にして実行する。`取得` が増えず、`対象外などで読まず` の回数が増えることを確かめる
6. 実画面の CPU を測るなら、手順 2 の実行中に別のターミナルで次を見る

   ```bash
   top -pid $(pgrep -n screen_check) -stats pid,cpu,mem
   ```

## 本人が実行する確認手順(Windows)

1. 「設定」→「時刻と言語」→「言語と地域」で日本語を追加し、OCR の言語機能が入っていることを確かめる。入っていないと `日本語の OCR の言語パックが入っていません` と出る
2. `cargo run -p zuchi-screen --release --example ocr_bench -- <画像のフォルダ>` で精度と時間を測る(画像は Mac で作って持っていく)
3. `cargo run -p zuchi-screen --release --example screen_check -- 30` で実際の取得を確かめる
