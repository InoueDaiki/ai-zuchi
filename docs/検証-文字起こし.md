# 検証: 文字起こし(zuchi-asr)

`crates/zuchi-asr` を Mac で測った記録。2026-11-01 時点。Windows では測っていない。

## 結論

- Rust のクレート(sherpa-onnx 2.0.1、静的リンク)で、VAD から文字まで通せた
- 劣化の影響は小さい。CER は clean の 7.7% に対し、最も悪い条件で 8.7%。Opus は 8 kbps でも clean と差がほとんどない。効くのは帯域で、8 kHz(電話相当)のときに約 1 ポイント悪化する
- 1 区間の処理は最大 0.3〜0.4 秒(負荷が低いとき)で、計算の補足の目標(発話の終わりから 3 秒)のうち大半は区切りの無音 0.8 秒の待ちが占める
- ピーク RSS は約 790 MB
- 実時間比は 0.04 で、当面の動作に支障はない
- 会議音声のためにしきい値を変える理由は見つからなかった。既定はしきい値 0.5、区切り 0.8 秒のままにする

## 設定

| 項目 | 値 | 理由 |
|---|---|---|
| VAD | `silero_vad.onnx`、しきい値 0.5 | 第一候補 |
| 区切りの無音 | 0.8 秒(既定) | 0.5〜0.8 秒の長いほう |
| 最大の区間 | 20 秒 | 同上 |
| 区間の前後 | 実音声 0.3 秒 + 無音 0.3 秒 | 足さないと CER が 25% まで悪化する。実音声はリングバッファに持つ |
| ASR | zipformer-reazon int8、greedy search、1 スレッド | 4 スレッドでも処理時間は 2 割ほどしか縮まない |
| 文字の除去 | 句読点を除いて 3 文字未満を捨てる | 雑音区間の平均 1.8 文字を落とす |

## 測定の結果

架空の 25 文を `say` の 5 声で読ませ、1〜3 秒の間を置いて並べた 831 秒の音声(125 発話)で測った。CER は表記のみで、NFKC と句読点の除去のあとに計算した。実時間比は VAD を含む処理の全体。

| clean(16 kHz) | 0.5 | 0.8 | 7.7 | 787 |
| clean(16 kHz) | 0.5 | 0.5 | 7.6 | 785 |
| clean(16 kHz) | 0.3 | 0.8 | 7.8 | 850 |

- どの条件でも区間は 125 個で、発話と一致した。発話の間が 1 秒以上あるので、区切りの違いは出にくい音声になっている。区切りの長さの効果は、この測定では確かめられていない
- 差の 0.5 ポイント未満は、誤り 1 件の出方で動く程度なので、意味のある差として読まない。音声は合成で、声も文も少ない

### 速度

同じ clean の音声で、スレッド数を変えて測った。計測機のロードアベレージは 1〜3 で、無負荷ではない。

| ASR のスレッド数 | 実時間比 | ASR の合計秒 | 1 区間の最大秒 |
|---|---|---|---|
| 1 | 0.039、0.041 | 29.8、31.4 | 0.32、0.39 |
| 2 | 0.033 | 23.8 | 0.25 |
| 4 | 0.032 | 21.9 | 0.24 |

モデルの読み込みは 0.9〜1.5 秒。他の処理と重なった実行では、実時間比が 0.11、1 区間の最大が 1.67 秒まで伸びた。

### 雑音だけの音声

定常の雑音に打鍵のような短い音を足した 5 分の合成音声では、しきい値 0.5 でも 0.3 でも区間が 0 個だった。VAD が誤検知しなかったので、**文字の除去の効果はこの測定では確かめられていない**。誤検知には話し声に近い雑音が要る。

### 短い発話

5 声で読ませた結果。

| 発話 | 結果 |
|---|---|
| はい、ええ、うん | 5 声とも出力なし |
| なるほど、そうですね、ありがとうございます | 5 声とも正しい |

短い相づちは落ちる。Kyoko の「はい」(0.3 秒)で除去を切って確かめると、区間そのものが 0 個で、文字の除去より前に VAD の段階で落ちていた。他の声と語は同じ原因か確かめていない。補足の判定には要らないので、「迷ったら黙る」に合わせて許容する。残したくなったら `VadConfig::min_speech_secs` と `AsrConfig::min_chars` の両方を見直す。

## 計測条件

| 項目 | 内容 |
|---|---|
| 計測機 | Apple Silicon の Mac、macOS 26 系 |
| 実行環境 | sherpa-onnx 2.0.1 の Rust クレート、静的リンク、CPU、release ビルド |
| 劣化 | afconvert で 8 / 12 kHz へ落として 16 kHz へ戻す。Opus は CAF へ符号化して復号する |
| ピーク RSS | `/usr/bin/time -l` の maximum resident set size。example が音声全体をメモリに持つ分(50〜100 MB ほど)を含む |

## 未検証と未解決

- **実際の人の声、実際の会議の音声。** 合成音声なので、残響、重なり、話し方の崩れを含まない。比べられるのは条件の間の差だけ
- **本物のパケット損失や会議アプリのノイズ抑制。** Opus の符号化だけで、ネットワークの影響は入っていない
- **雑音区間の文字の除去の効果。** 上記のとおり
- **最大の長さで切った区間のつなぎ目。** 切った直後は後ろの実音声がまだないので足せない。次の区間の頭の 0.3 秒は前の区間と重なるため、文字が重複する可能性がある。CER は測っていない
- **長時間の連続動作でのメモリリーク。** 14 分の音声までしか流していない
- **Windows。** 速度もメモリも未測定。ビルドは CI でのみ確かめる

## 再現の手順

macOS で実行する。`say` と `afconvert` を使う。

```bash
mise run models:fetch
cargo build --release -p zuchi-asr --example transcribe
python3 crates/zuchi-asr/scripts/measure.py <作業ディレクトリ>
```

1 つの WAV を文字にするには次のようにする。

```bash
cargo run --release -p zuchi-asr --example transcribe -- 音声.wav
```

`.cargo/config.toml` は Windows のときだけ効く。sherpa-onnx の Windows 向け静的ライブラリが `/MT` なので、Rust 側も静的 CRT に揃えている。
