# 設計メモ

決定事項とその理由を残す。2026-11-01 時点。検証していないものは「要検証」と書き、決定事項として扱わない。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 位置づけ | 個人用。配布と商用化は当面考えない | 判定の質を上げることに集中する |
| 対応 OS | macOS 14.2 以降と Windows 11 | PC の音声の取得に使う API の下限が理由(Windows の下限は要検証) |
| 画面への出し方 | 常に手前のオーバーレイに文字で出す | 会議中に声を出すと邪魔になる。音声の読み上げは作らない |
| 既定の振る舞い | 迷ったら黙る | 適合率を再現率より優先する |
| 計算 | LLM は数値の抽出だけを行い、計算はコードで行う | 数字の誤りは信用を一度で失う |
| 外への通信 | 検索語、モデルの取得、Ollama(localhost)だけ | 会議の内容が流出しないようにする |
| 音声の保存 | ディスクに書かない | 文字起こし後に捨てる |
| 行動 | 本人の操作なしに外部へ影響することをしない | 誤認識と、後述のプロンプトインジェクションへの備え |
| 話者 | 当面はマイクを「自分」、PC の音声を「相手」として扱う | 話者識別なしでも、会議の用途の大半は足りる |
| リマインドの保存先 | まずアプリ内(暗号化された記憶のファイル)に置く。外部のサービスは使わない | 外へ出さずに使用例 3 を完結させる。Apple Reminders などへの連携は必要になってから考える |

## 全体の構成

重い処理ほど、呼ばれる回数を減らす。

| 段階 | 処理 | 動くとき | 計算の重さ |
|---|---|---|---|
| 0 | VAD、画面の変化の検知 | 常時 | ごく軽い |
| 1 | 文字起こし、OCR | 発話時、画面の変化時 | 軽い |
| 2 | ルールによる絞り込み | 文ができるたび | ごく軽い |
| 3 | LLM による判定 | 段階 2 を通ったときと、一定の間隔 | 重い |
| 4 | スキルの実行、確認 | 段階 3 で口を出すと決めたとき | 重い |

- 段階 2 は、数と単位、疑問の表現、依頼の表現、固有名詞などの手がかりを見る。ただし、ここで落としすぎると良い補足も消えるので、手がかりは緩くし、評価で調整する
- 段階 3 は JSON で「スキル、理由、確信度」を返す。LLM の呼び出しは同時に 1 つに絞り、古い判定の待ち行列は捨てる

### スキル

| スキル | 手順 | 通信 |
|---|---|---|
| 計算 | 数値と単位を抽出し、コードで換算する | なし |
| 検索 | 検索語を作り、検索し、結果の範囲で 1 文に要約する | 検索語のみ |
| 記憶 | 過去の文字起こしとメモから探す | なし |
| 提案 | 依頼や期限を見つけ、リマインドなどの操作を提案する | なし |

使用例 1 の答えは、3 カ月を 91 日とすると秒間約 127 件、1 日約 1,100 万件。前提の日数も画面で確かめられるようにする。

### 口を出す前の確認

文字列を画面に出す直前に、機械的に確認する。

- **根拠:** 検索の補足は出典を持つ。記憶の補足は元の発言を持つ。根拠がなければ出さない
- **重複:** 同じ話題に一定の時間内は 1 度だけ
- **頻度:** 補足の数に上限を置く。無視が続いたら間隔を延ばす
- **鮮度:** 話題が移ったら捨てる

## 使われ方と評価

作る順番を決める基準は、「文字起こしの精度」より「このひとことは嬉しいか」に置く。

**目標(初期値。測ってから見直す)**

| 指標 | 目標 |
|---|---|
| 計算の補足が出るまで | 発話の終わりから 3 秒以内 |
| 検索の補足が出るまで | 発話の終わりから 10 秒以内 |
| 補足の適合率 | 80% 以上(出した補足のうち嬉しかったもの) |
| 1 時間の会議での補足の数 | 5〜15 件 |
| 待機中の CPU | ノート PC で 1 コアの 10% 以内 |

**評価**

- 架空の会話と画面の台本で、「口を出すべき場面」と「黙るべき場面」を固定のデータセットにする。音声がなくてもテストできるように、文字起こしの段階から流せる形にする
- 誤った補足、余計な補足、見逃しを別々に数える
- 個人の会話を含むデータはコミットしない

## プライバシーと安全

会議の相手は録音に同意したわけではない。性能より先に、ここを決めておく。

- 音声はメモリの中だけで扱う。文字起こしと OCR の文字列は暗号化して保存し、保持期間を設定できるようにする
- 聞いていることを、メニューバーなどで常に見える形にする。ワンクリックで止められるようにする
- パスワードマネージャーや銀行のアプリなど、対象外のアプリやサイトを設定できるようにする。パスワード欄の周辺も読まない
- 解析とクラッシュレポートの SDK は入れない
- 検索語は会話の文をそのまま使わず、固有名詞と話題に絞る。検索の履歴を本人が見られるようにし、検索そのものを切れるようにする。社外秘の名前が検索語に混ざる可能性は残るので、除外語のリストと確認モードを用意する
- 社内の規則や相手の国の法律によっては、会議の文字起こしに同意が要る。使う場の判断は本人が行う

### プロンプトインジェクション

画面、会議の音声、Web の内容は、どれも他人が書けるものなので、**データとして扱い、指示として扱わない**。

- 外部の内容を読むプロンプトと、操作を実行する権限を分ける
- 検索語の作成に Web の内容を使わない(誘導された検索で情報が漏れるのを防ぐ)
- スキルの一覧は固定にする。LLM から任意の URL やコマンドを実行できないようにする
- 操作の内容は、実行の前に本人に見せて確認する

### リマインド

提案は `ProposedAction` のまま画面へ渡し、カードの「リマインドをセット」を本人が押したときにだけ実行する。

- **実行の経路:** 判定(`zuchi-pipeline`)は `zuchi-runtime` にも `zuchi-memory` にも依存せず、記憶も `MemoryStore` の trait でしか触らない。リマインドの追加はこの trait に載せないので、LLM の出力から登録する経路がない。操作の中身は画面から受け取らず、出した補足のものを使う
- **期限:** LLM は期限を決めない。指定がなければ受け付けてから `DEFAULT_REMINDER_DELAY`(30 分)の後とし、カードにも実行の前に見せる
- **通知:** 30 秒ごとに確かめ、知らせたら印をつける。起動していない間に過ぎたものは次の起動で知らせ、一度に 4 件以上ならまとめて 1 件にする。一時停止中も知らせる。聞くのを止める操作で、本人が頼んだ予定まで止めないため
- **通知の許可:** アプリからは変えない。デスクトップのプラグインは許可の状態も失敗も返さないので、切られていても分からない。そのため期限切れはメニューバーの「リマインド一覧」にも出す
- **題名:** 画面や会話から作られ、他人が書ける。通知とメニューには改行、制御文字、文字の向きを変える文字を除いた 1 行で出し、メニューの `&` は文字として出す。ログには書かない
- **保持:** 未完了は本人が完了にするまで残し、完了したものは出来事と同じ保持期間で消す

## 記憶と成長

| 層 | 内容 | 保持 |
|---|---|---|
| 作業の記憶 | 直近 5〜10 分の会話と画面 | メモリのみ |
| 出来事 | 文字起こし、要約、補足とその反応 | 設定の期間 |
| 知識 | 人、プロジェクト、用語、決定事項 | 本人が消すまで |
| 好み | どんな補足が嬉しいか | 本人が消すまで |

「育てる」の仕組みは次のとおり。

- 補足への反応(役立った、不要、無視)を記録する。判定のプロンプトには、似た場面の過去の反応を例として添える
- 固有名詞を辞書に覚える。文字起こしの誤りの訂正にも使う
- 覚えた内容を本人が一覧で見て、直したり消したりできるようにする
- モデルの学習はしない

## 技術の選択

### アプリの基盤: Tauri 2

Rust で常駐部分を軽く書け、画面は慣れた React を使える。Electron は常駐のメモリが重く、Python は配布と OS API の扱いが難しい。

- ビジネスロジックは OS に依存しない Rust のクレートに置き、音声、画面、通知は trait の裏に隠す
- macOS の Core Audio tap は Rust から直接使いづらいとの報告があるので、Swift の補助プログラムに分ける([解説](https://dev.to/baurzhan_zhetenov_442c4cd/how-i-capture-system-audio-and-transcribe-it-locally-with-no-server-in-the-loop-tauri-rust--4a0n)、個人の記事なので要確認)
- Windows の loopback は [tauri-plugin-system-audio](https://docs.rs/crate/tauri-plugin-system-audio/latest) のように Rust で書ける

### LLM: Ollama

ユーザーの指定どおり、Ollama を第一候補にする。手元には 0.40.13 が入っている。アプリには同梱せず、別に入れて HTTP で使う。LLM の呼び出しは trait に隠し、llama.cpp などへ差し替えられるようにする。

- モデルの候補は Gemma 4 E4B。比較に Qwen3 系を使う
- 「日本語向けの小型モデル」を評価なしで選ばない

### 文字起こし: 発話区間ごとの処理

手元で測った結果は [検証-文字起こし.md](検証-文字起こし.md) にある。

- ストリーミングのモデルは CER がほぼ 2 倍だったので使わない。発話の区切りを待つぶん遅れるが、補足の用途では許容できる見込み
- 区間の前後に音声を足す、幻の短文を除く
- どちらも ReazonSpeech で学習したモデル。データセットの利用条件との関係は確認が要る。個人用のうちは保留にし、配布するなら見直す
- 会議の音声は、同じ VAD のしきい値で動くとは限らない。圧縮された音声で測り直す

### 画面: まず OCR

画面の変化を検知し、変わった領域だけを OS の OCR(macOS は Vision、Windows は Windows.Media.Ocr)で読む。視覚モデルは重いので、常時は使わない。OCR で足りないときに限って試す。

- 自分のオーバーレイは取得の対象から外す。自分の補足に自分で反応するのを防ぐ
- 画面共有にオーバーレイが映らないようにする。OS と会議アプリの組み合わせによって効かない可能性があるので、要検証

### Web 検索

自前の SearXNG を既定にし、不安定なら Brave Search API に切り替える。比較は [検証-検索.md](検証-検索.md) にある。

## 先に解くべき難所

1. **口を出す判定の質。** このプロダクトの価値はここで決まる。最初の検証の対象にする
2. **手元のモデルの遅さと発熱。** 会議のアプリと同時に動かす。M5 の 32 GB でも余裕があるとは限らず、Windows は GPU の有無で大きく変わる
3. **文字起こしの誤りへの強さ。** 「BONX」のような固有名詞は崩れやすい。画面の文字と辞書で補えるか試す
4. **マイクへの回り込み。** スピーカーで聞くと相手の声がマイクに入り、「自分」と重複する。当面はイヤホンを前提にし、後からエコーキャンセルか重複の除去を足す

## 進め方

| 段階 | 内容 | 完了の条件 |
|---|---|---|
| 0 検証 | 台本のデータセットを作り、Ollama で判定の質と速度を測る | 判定が使えると分かる |
| 1 耳 | Mac でマイクと PC の音声を文字起こしし、オーバーレイに計算の補足を出す | 実際の会議で使用例 1 が動く |
| 2 調べもの | 検索と、根拠の確認を足す | 使用例 2 が動く |
| 3 目 | 画面の OCR とリマインドの提案を足す | 使用例 3 が動く |
| 4 記憶 | 長期の記憶と、反応からの学習を足す | 過去の会議の内容で補足できる |
| 5 Windows | Windows の音声と画面の実装を足し、測り直す | Windows で使用例 1〜3 が動く |

Windows は最後に回すが、段階 1 から OS に依存する部分を trait に隠し、CI で Windows のビルドを通す。
