# 検証: 音声取得

`crates/zuchi-audio` の動作を実機で確かめる手順と、これまでに分かったこと。2026-11-01 時点。

権限の許可は本人にしかできない。下の手順は、**本人が普段使うターミナルで**実行する。音声は保存されず、表示されるのはフレーム数とピーク音量だけ。

## 手順

権限は、実行したプログラムではなく、起動元のアプリ(ターミナルなど)に対して記録される。別のアプリから起動すると結果が変わる。

### PC の音声(macOS)

```bash
cargo run -p zuchi-audio --example capture_check -- system --seconds 6 --play
```

`--play` は取得の途中で効果音を鳴らす。これで「権限がない無音」と「鳴っていないだけの無音」を見分ける。音量が 0 でも結果が変わる可能性があるので、聞こえる音量で実行する。

初回はシステムオーディオ録音の許可を求められることがある。ダイアログが出ずに「音を鳴らしたのに無音」となったら、システム設定の「プライバシーとセキュリティ」→「画面とシステムオーディオの録音」→ 下の「システムオーディオ録音のみ」に、使っているターミナルを追加してオンにし、ターミナルを開き直して再実行する。

### マイク

```bash
cargo run -p zuchi-audio --example capture_check -- mic --seconds 5
```

実行中に声を出す。初回は許可を求められる。ダイアログに答えるまで開始が戻らないことがあり、30 秒で「開始が終わりません」のエラーになる。拒否した場合や出ない場合は、システム設定の「プライバシーとセキュリティ」→「マイク」でターミナルをオンにする。

### 結果の読み方

| 表示 | 終了コード | 意味 | 次にすること |
|---|---|---|---|
| 音が取れています | 0 | 成功 | なし |
| 権限が拒否されていて無音です | 2 | OS の記録が「拒否」 | 上の設定で許可する |
| 音を鳴らしたのに無音です | 2 | 権限がない可能性が高い | 上の設定で許可する。許可済みなら音量と出力先を確認する |
| 無音です | 1 | 鳴っていないだけかもしれない | `--play` をつけて再実行する |
| 音を鳴らしたのにフレームが届きません | 1 | 出力デバイスの問題 | 既定の出力を確認する |
| 開始に失敗 / 開始が終わりません | 1 | 取得を始められない | 表示された理由を読む。後者はダイアログを確認する |

`権限の状態` の行は、TCC の非公開 API を読むだけの参考情報で、設定は変更しない。`Undetermined` は「尋ねられていない」を意味する。アプリの動作はこの値に依存させず、取得を止める理由にも使わない。

## 確かめたこと

Apple Silicon、macOS 26.6.2。Claude Code の中から実行したので、権限は未許可(`Undetermined`)のまま。

| 項目 | 結果 |
|---|---|
| 補助プログラムの起動と tap の開始 | 動いた。エラーにならず開始した |
| 権限なしの PC の音声 | 効果音を鳴らしても、ピークが完全に 0 のフレームが届いた。エラーにはならない |
| PC の音声の停止 | 終了後に補助プログラムのプロセスが残っていないことを確認した |
| 親が落ちたとき | 親を `kill -9` すると、補助プログラムも stdin の EOF で終了した |
| 権限なしのマイク | ダイアログを待つとみられる状態で、ストリームの作成が戻らなかった。開始を 30 秒で打ち切るようにし、時間切れのエラーになることを確認した |

**実際の音が取れることは、まだ確かめていない。** 本人が上の手順で確かめる。

## 分かったこと

- **権限がないと無音になるだけ。** tap は成功し、ゼロのバッファが届く。信号だけでは本当の無音と区別できないので、自分で音を鳴らして見分ける
- **macOS の tap も、何も鳴っていない間はフレームが届かない。** 無音のまま 10 秒取得するとフレームは 0 だった。鳴らし始めると届き始める。権限を許可した状態でも同じかは未確認。後段の VAD や文字起こしは、フレームが届かない時間があることを前提にする。Windows の loopback も同じ
- **Windows の loopback は、cpal が対応している。** 出力デバイスから入力のストリームを作ると loopback になる。CI のビルドとテストまでで、実機では確かめていない

## 判断: macOS の PC の音声は Swift の補助プログラムにする

cpal 0.18 は macOS の loopback にも対応しているので、Rust から直接使う案も比べた。次の理由で採用しなかった。

| 理由 | 内容 |
|---|---|
| 入出力を持つデバイスで誤動作する | cpal は `supports_input()` なら通常の入力として開く。USB ヘッドセットのように入出力を持つデバイスが既定の出力だと、PC の音声ではなくマイクが録れる |
| 対応 OS | cpal の loopback は macOS 14.6 以降。設計メモの下限は 14.2 |
| 出力先の変更に追従しない | tap が特定のデバイスに結びつく。補助プログラムは既定の出力の変更で作り直す |
| デバイスの設定に触る | cpal はストリームの作成時に、出力デバイスの物理フォーマットを設定しにいく |

補助プログラムは `build.rs` が `swiftc` でビルドするので、別の手順はいらない。アプリへ同梱するときは `SystemSource::with_helper` で場所を渡す。

## 残っている確認

- 実際の音が取れること、ピークが妥当なこと(本人の実行が必要)
- 許可済みの状態で、何も鳴っていないときにフレームが届くか
- 再生中に出力先を切り替えたときの追従(イヤホンの抜き差しなど)
- Tauri アプリに組み込んだときの権限の扱い。アプリの Info.plist に `NSAudioCaptureUsageDescription` と `NSMicrophoneUsageDescription` が必要になる見込み
- Windows の実機での loopback とマイク
- 取得を止めたあとの CPU、長時間の取得での遅れ
